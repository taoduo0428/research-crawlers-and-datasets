# 后面写说明，按这个习惯来

仓库是给课题组同学用的，写得清楚比写得正式重要。

- **先说它做什么。** 比如「这份脚本用来补猎聘的岗位 JD」，不要开头写一段空泛的项目价值。
- **说清文件在哪。** 用真实路径和文件名，让别人能照着找到。
- **给能执行的命令。** 运行目录、依赖和前置条件要写出来。没有实际验证过，不要写「一键运行」「完整支持」。
- **数据写准。** 哪张是主表、哪张是子集、哪些行重复、哪些字段为空，都要讲明白。时间记具体日期，不要用「最新」代替。
- **别把问题藏起来。** 缺原始数据、没拿到详情、测试只跑了离线部分，就直接说。
- **用正常说话的语气。** 少用「赋能」「闭环」「多维度」「高质量交付」「全面覆盖」这类套话；也不用每段都加粗和喊注意。
- **历史记录少改事实。** 以前的版本号、测试结果、原始报错和决策过程需要保留。可以在最前面注明「这是当时的记录，当前入口看哪里」。
- **别修改工具指令。** `SKILL.md`、`AGENTS.md`、`specs/` 中有些内容是给自动化工具或研发流程使用的，不是给人看的项目介绍；不要只为了润色把指令和测试记录改坏。

以后新增项目 README，可以照着回答四个问题：**这里是什么？代码从哪运行？数据在哪？还有哪些坑？** 四个问题说清楚就够了。
