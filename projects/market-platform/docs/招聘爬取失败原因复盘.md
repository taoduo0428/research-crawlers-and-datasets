# 招聘爬取失败原因复盘

## 结论

前面 BOSS 和猎聘反复出现登录墙、安全验证、改密和空详情，不是单一请求参数造成的。主要是列表采集和详情采集混在一起、多浏览器/多账号/多 Profile 反复切换、详情页连续高频访问，以及会话在真实浏览器和采集 Profile 之间复制。猎聘登录态全部消失还有一个已经定位到代码行的直接原因：采集器在真实 Edge Profile 上执行了清空 Cookie。

## 为什么最初有岗位但没有 JD

最初两个站点的主采集器主要读取岗位列表或列表接口。列表中有职位名称、薪资、公司、分类和详情链接，但完整岗位职责只在详情页。因此原始数据有岗位元数据，`description_raw` 却为空。前程无忧不同，它的岗位搜索响应直接返回 `jobDescribe`，所以第一次采集就能拿到 JD。

后续把流程拆成“先稳定取得列表和详情 URL，再按断点慢慢补详情”，避免重新跑完整职业目录，也避免同一岗位重复访问。

## 为什么本地登录后，另外几个浏览器一度也能用

实测中这些浏览器并非完全独立：

- 项目中的 `.crawler-state/edge-default-link` 是指向真实 Edge `User Data` 的 junction，不是副本。
- 一些采集 Profile 是从真实 Edge Profile 克隆出来的，Cookie 使用同一台 Windows 的同一加密密钥。
- 部分运行过程还会从当前浏览器同步或复用会话状态。

因此在本地 Edge 完成人工登录或验证后，随后启动的进程如果仍连接真实目录、使用刚生成的克隆，或同步了当前会话，就会带上可用 Cookie，看起来像“本地登录一次，其他三个也自动恢复”。这不是网站允许任意匿名浏览器，也不能作为稳定机制。

如果三个浏览器确实完全独立、没有共享或复制任何会话，本地登录最多可能暂时改善同一出口 IP 的服务端风险状态；本项目没有足够证据证明这一点，不能把它当成确定原因。

## 为什么其他网站登录态全部消失

猎聘详情工具原逻辑在识别到登录页或安全中转页时执行：

```python
context.clear_cookies()
```

本意是让一个隔离 Profile 退回匿名状态再试一次，但运行时 `edge-default-link` 直接连接了真实 Edge 用户目录。`clear_cookies()` 的作用范围是整个浏览器 Context，不只猎聘域，因此真实 Profile 中其他网站的 Cookie 也被清空。历史、书签和密码库仍在，消失的是网站登录会话。

代码已改为遇到登录/安全页时保留 Cookie 并停止，不再自动清空或匿名重试。项目中已找到清空前的可信 Profile 副本，包含 2,704 条 Cookie、937 个域，并且加密密钥与当前 Profile 一致；恢复前必须完全退出 Edge并备份当前 Cookie 库。部分网站若已在服务器端撤销旧会话，即使恢复本地 Cookie 仍需重新登录。

## 风控反复触发的原因

以下因素在前面的运行中叠加出现：

- 同一账号在多个新 Profile 或不同浏览器环境中使用；
- Cookie 被导出、注入、再次导出，账号、IP、设备状态关联不稳定；
- 多个详情 worker 并发访问，短时间内访问大量相似 URL；
- 失败后马上重启、换账号或重新注入，增加异常登录和设备变更；
- 对暂停招聘、失效或已经成功的岗位重复访问；
- 列表翻页与每条详情访问同时进行，请求密度明显高于正常浏览。

触发后继续加速或轮换账号，只会放大同一出口 IP 和设备环境的异常信号。验证码、改密和安全中心不是普通网络错误，不能按 500/超时逻辑自动重试。

## 后续正确做法

稳定方案是固定一个专用 Profile，列表和详情分开，详情队列以 `record_id` 去重并永久记录成功状态。单个进程、单个页面顺序处理；遇到登录墙、安全页或连续空 JD 立即保存断点并停止。不要连接日常使用的真实 Edge `User Data`，不要无条件清 Cookie，不要让多个进程写同一个 Profile 或 SQLite。

对于已经取得的历史岗位，只补缺失 JD，不重新访问已有成功记录。前程无忧优先使用列表 API 已返回的 JD；猎聘只有详情缺失时才进入详情页。这样请求量由“每次重跑全部岗位”降低为“只处理新增或缺失岗位”。
