## Adaptive target-opening wait — 2026-09-17

- Added an experimental readiness probe for the URL-open 8-second wait and timestamp-detail 2+8-second waits. **It is disabled by default after real-device calibration did not establish a stable speedup.** Ordinary API jobs retain the original waits and UI snapshot/recovery path, with new timing diagnostics. Explicit `-EnableAdaptiveTargetWait` on the runner/opener is required to exercise the experiment. Probe work consumes the existing wait budget; ID-only search retains its existing waits.
- Early continuation requires the existing strict target verifier within the fresh capture-line boundary, a uniquely mapped target Story, matching visible author and distinctive body prefix, an actionable post control, and no loading/search/offline/foreign/ANR surface. Timestamp promotion additionally requires an actionable detail composer and close control. Mere Reel prefetch, another post's content, hidden/zero-area nodes, and a target link quoted in another post cannot prove readiness. The final strict analyzer and downstream source/terminal guards still run.
- XML visibility is inherited, while Android `enabled` is checked on each node itself. Real Facebook XML has disabled layout containers around enabled interactive children; cascading `enabled=false` would incorrectly reject these pages. This matches the per-View state in [Android View source](https://android.googlesource.com/platform/frameworks/base/+/HEAD/core/java/android/view/View.java). Detail controls may be siblings of the content list rather than descendants of its nearest author/body container.
